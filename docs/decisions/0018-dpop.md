# 0018. Phase 3: DPoP proofs, and what verifies their JOSE

- **Status:** proposed, 2026-11-14
- **Decision needed from:** Terra Howard, because it is a dependency choice of the kind she made in decision 0005

## Context

Phase 3 of decision 0015 enforces `cnf` and `catdpop` (CTA-5007-B section 4.8). A `cnf` claim with the `jkt`
method holds the RFC 7638 JWK SHA-256 thumbprint of a DPoP public key, and a recipient must refuse the token unless
the request carries a DPoP proof made with that key, verifiable as RFC 9449 describes. `catdpop` adjusts how the
proof is checked: a window for its `iat`, how `jti` is handled, and a list of critical settings. Recipients must
support ES256 for these proofs.

A DPoP proof is a JSON Web Token signed as a compact JWS, carrying its public key as a JWK in its header. So phase 3
needs JSON Web Signature verification, JWK parsing and RFC 7638 thumbprints. Nothing in this repository does JOSE
yet. Until phase 3, tokens with `cnf` or `catdpop` are refused as unsupported.

## Options

- **A. A JOSE library,** such as go-jose. Broad algorithm support and years of use by others. Its licence,
  maintenance and the size of what it pulls in would need checking first; AGENTS.md asks for standard library first.
- **B. A minimal JWS verifier of this project's own,** on the standard library: `encoding/json`, `encoding/base64`
  and `crypto/ecdsa` (with `crypto/rsa` if PS256 proofs are wanted). It would accept only the compact
  serialization, only the algorithms allowed, and only the header fields RFC 9449 uses (`typ`, `alg`, `jwk`). This
  mirrors decision 0005, which took a CBOR library but wrote the small COSE layer here. Outside vectors exist: RFC
  7638 has a worked thumbprint, and RFC 9449 has example proofs.
- **C. Defer phase 3,** and build the HTTP integration package first (finding the token in a request, removing it
  from the URI before `catu`, `Cache-Control: private`), which every deployment needs and which needs no
  dependency.

## Recommendation

B, then phase 3; or C first if you would rather see the package usable behind a server before adding proof of
possession. B keeps the dependency list at one and the code small enough to mutation-test as thoroughly as the
rest. JOSE has a history of library flaws in exactly the parts B would leave out (algorithm `none`, header-supplied
keys, JWE), so a deliberately narrow verifier is a strength here, not a shortcut. The DPoP key does come from the
proof's own header, as RFC 9449 intends; what makes that safe is matching its thumbprint to the `jkt` in the
already verified token.
